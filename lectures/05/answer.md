- 検索だけを実行して見つかったページと、その本文で確認できたこと：`uv run python -m app.retrieval "LoRA QLoRA 違い"` を実行した。検索結果は第2回p.52、p.51、p.60、p.47、p.61の順だった。1位のp.52には、LoRAが元の重みWを固定し、低ランク行列A・Bを学習すること、QLoRAが元の重みを4bitに量子化することが明記されていた。2位のp.51も同じ内容を補足していた。残り3ページは関連する話題だったが、今回の回答には直接必要なかった。
- `--trace`で見えたツール呼び出し：全文投入は検索ツールなし（モデル応答1回）。ベクトル検索はsearch_materials({'query': 'LoRA QLoRA 固定 学習'})を1回（モデル応答2回）。Treeはbrowse_treeを4回（モデル応答5回）。引数は順に{}、{'node_id': 'lec02-main'}、{'node_id': 'lec02-main-s045'}、{'node_id': 'lec02-main-p052'}。Graphはsearch_graph({'query': 'LoRA 固定 QLoRA'})を1回（モデル応答2回）。Graphのseeds/expandedの詳細なページ一覧は未記録。
- 取得した情報が足りなかった例、取得できたのに回答へ使えなかった例：今回のLoRA・QLoRAに関する質問では、4方式とも必要な根拠を取得し、正しく回答できたため、明確な情報不足や回答失敗は確認されなかった。一方、ベクトル検索では第2回p.60、p.47、p.61も取得されたが、これらは今回の質問への直接的な根拠としては不要だった。検索結果が多いことが、必ずしも回答の質の向上につながるわけではないと考えられる。
- 今回の用途に採用したい方式と、その理由・比較条件の限界：単一ページに答えがある質問では、ベクトル検索を第一候補としたい。4方式とも正答し、ベクトル検索の入力トークン数と生成API推定費用が最少だったため。ただし、全文投入のみ対象資料が広く、実行は各1回のため、応答時間も含めた一般的な優劣は判断できない。
- 気づき・疑問：全文投入が最短時間で回答したことが意外だった。Treeは目次を段階的に探索するため、モデルとのやり取りが増えて時間がかかる可能性がある。単一ページで答えられる質問では、Graphで関連ページを増やす利点が限定的かもしれない。複数ページにまたがる質問では結果が変わるか確認したい。

- 取り組んだレベル：実装

- やったこと：
  `app/retrieval.py` の `search()` を改良した。
  ベクトル検索で取得したページに加え、同じ document_id の
  前後1ページの本文も取得する処理を追加した。
  ページの重複は seen を使って除外した。
  埋め込みモデルや検索DBは変更していない。

- 比較した質問と固定条件：
  質問「第3回の説明では、コンパクションとセッションをまたぐ
  メモリはどう違いますか。日々のメモはすべて長期メモリに入りますか」
  モデル：gemini-3.5-flash-lite
  対象資料：第1〜3回の講義資料
  同じ質問を --trace 付きで実行した。

- 結果：
  変更前：3.94秒、入力2496 tokens、出力439 tokens、
  推定費用 $0.001846。
  変更後：6.30秒、入力4322 tokens、出力483 tokens、
  推定費用 $0.002504。
  変更後の検索単体では、重複除去後11ページを取得した。
  変更前後とも、p.39、p.40などを根拠に、
  コンパクションとセッション間メモリの違い、
  日々のメモの選別について正しく回答した。

- 改善した例と、残る失敗・制約：
  前後ページの本文も取得できるようになり、
  複数ページに情報が分散している場合に対応しやすくなった。
  一方、今回の質問では変更前から正しく回答できており、
  明確な回答品質の改善は確認できなかった。
  不要な周辺ページも追加され、入力トークン数と費用が増加した。
  また、モデルが生成した検索語が変更前後で異なるため、
  検索範囲の拡張だけの効果とは断定できない。

- 気づき・疑問：
  RAGでは検索件数や取得範囲を増やすだけでなく、
  必要な文脈を選択的に取得する設計が重要だと考えた。
  今後は、前後ページを無条件に追加する方法と、
  関連性に応じて追加する方法を比較したい。
